Building an Hypervisor: How AMD SVM Saves Host State Across #VMEXIT

Over the past few weeks, I have been exploring the world of hypervisors, mainly type-2; in oder to better understand how anti-cheat systems and EDRs work. Thus, I have decide to start coding one myself to dive in better and see their relationship to Windows internals (which is why this post is in the Windows Internals section).

Almost all of my progress in development is documented in a short series of silent videos I recorded while simply coding completely avoiding the use of artificial intelligence so I could enjoy programming in its purest form.

If you are interested check: https://www.youtube.com/watch?v=-bcyGHkD1b0&list=PLWywTdBGseJs

SVM Arch Reference Manual

As we said in the description of the blog, I will show you how I code a function with its own headers from a section of a large manual. The manual will be: AMD64 Virtualization Codenamed “Pacifica” Technology: Secure Virtual Machine Architecture Manual (33047—Rev. 3.01—May 2005).

resource: https://www.mimuw.edu.pl/~vincent/lecture6/sources/amd-pacifica-specification.pdf

Look for the paragraph in 2.2.1 Basic Operation (Section 2.2 VMRUN Instruction, Chapter 2: SVM Processor and Platform Extensions). It first talks us about the VMRUN instruction being the cornerstone of SVM, here we will know that the instruction takes an unique argument, namely VMCB (Virtual Machine Control Block); so, to start our journey lets dive into our favorite documentation: MSDN -> https://learn.microsoft.com/en-us/%20cpp/intrinsics/svm-vmrun?view=msvc-160

Learning about __svm_vmrun, the function uses a minimal amount of information in the VMCB to begin executing the virtual machine guest code and it is equivalent to the VMRUN machine instruction. Since Microsoft’s documentation is simply wonderful, they’ll refer you to a nonexistent external source (the manual).

void __svm_vmrun(
   size_t VmcbPhysicalAddress
);

From here, we could just asume we need to create a C data-structure with the following content:

a list of which instructions or events in the guest (e.g., write to CR3) to intercept various control bits that specify the execution environment of the guest or that indicate special actions to be taken before running guest code, and guest processor state (such as control registers, etc.).

Confused, right? If we continue reading the manual the will talk us about the basic operation where you will learn the enviroment that you need to execute VMRUN instruction, topic that we wil not dive in the blog but good to know, for future coding.

2.2.1[.1] Saving Host State

Continuing with a passage that we probably won’t fully understand we found the subsection: Saving Host State, this will be the keystone, core, pillar; whatever you want to name it of the blog. And it tell us:

Saving Host State. To assure that the host can resume operation after #VMEXIT, VMRUN saves at least the following host state information at the physical address specified in the new MSR, VM_HSAVE_PA:

  • CS.SEL, NEXT_RIP—The CS selector and RIP of the instruction following the VMRUN. On #VMEXIT the host resumes running at this address.
  • RFLAGS, RAX—Host processor mode and the register used by VMRUN to address the VMCB.
  • SS.SEL, RSP—Host’ stack pointer.
  • CR0, CR3, CR4, EFER—Host’s paging/operating mode.
  • IDTR, GDTR—The pseudo-descriptors. (VMRUN does not save or restore the host LDTR.)
  • ES.SEL and DS.SEL.

Processor implementations may store only part (or none) of host state in the memory area pointed to by VM_HSAVE_AREA and may store some or all host state in hidden on-chip memory. Different implementations may choose to save the hidden parts of the host’s segment registers as well as the selectors. For these reasons, software must not rely on the format or contents of the host state save area, nor attempt to change host state by modifying the contents of the host save area.

Structure Creation

It’s a bit clearer this time around. Based on what the manual just told us, lets map out a simple to-do list for our headers:

  • Segment Registers (CS, ES, DS, SS)
  • Pseudo-Descriptors (IDTR & GDTR)
  • Control Registers & MSR (CR0, CR3, CR4, EFER) + RFLAGS

_HOST_STATE Data-structure

Following up on what we mentioned just before, we could create the following default C-structure:

typedef struct _HOST_STATE {
  _HOST_STATE() = default;

  // Segment Registers (*CS, ES, DS, SS*)
  register cs;
  register es;
  register ds;
  register ss;

  // Pseudo-Descriptors (*IDTR & GDTR*)
  register idtr
  register gdtr

  // Control Registers & MSR (*CR0, CR3, CR4, EFER*) + RFLAGS
  UINT64 efer;
  UINT64 cr4;
  UINT64 cr3;
  UINT64 cr0;
  UINT64 eflag;

} HOST_STATE, *PHOST_STATE;

We declare _HOST_STATE() = default to preserve the compiler-generated constructor without adding overhead or altering the struct’s memory layout for low-level operations.

register Data-structure

Later on, we will see that segment registers are mainly splitted in a few parts:

  1. selector
  2. limit
  3. attribute
  4. base address

In fact, wikipedia show us 3 of these 4 parts, missing up the attribute section. The photo is related with the Local Descriptor Table (LDT), but I found a better picture of the Segment Registers in nixhacker.com:

https://nixhacker.com/segmentation-in-intel-64-bit/ https://en.wikipedia.org/wiki/X86_memory_segmentation#/media/File:Protected_mode_segments.svg

Despite the structure is for intel 64 bit, we get the concept. Furthermore, by reading one of our favorite github projects that maybe you have hear of… linux, we can find the struct for a Segment Register:

// https://github.com/torvalds/linux/blob/master/arch/x86/include/asm/svm.h#L320

struct vmcb_seg {
	u16 selector;
	u16 attrib;
	u32 limit;
	u64 base;
} __packed;

In the project krakenvm-mg we can find the same structure but instead of using u16 datatype for attributes he uses is own structure, keeping it similar to nixhacker.com resource.

To sum up, adding Windows conventions isntead of Linux one’s, this will be our final structure for segment registers:

typedef struct _seg_register {
    UINT64 base_addr;
    UINT32 limit;
    UINT16 selector;
    union attribute {
        UINT16 value;

        struct {
            UINT16 type : 4;
            UINT16 system : 1;
            UINT16 dpl : 2;
            UINT16 present : 1;
            UINT16 avl : 1;
            UINT16 longmode : 1;
            UINT16 def_bit : 1;
            UINT16 granularity : 1;
            UINT16 reserved : 4;
        };
    } attribute;

Taking advantage of the work done in krakenvm-mg we add another way to store local registers and eflags. To be honest, in this structure we only use the eflags data, but as the manual mentions some local registers as rax, rip, rsp better to add it and not use it than to need it and not have it.

// https://github.com/wizardengineer/krakensvm-mg/blob/main/krakensvm/inc/hv_util.hpp#L110

struct _register_ctx_fmt_t {
  UINT64 rax;
  UINT64 rip;
  UINT64 rsp;
  UINT64 eflag; //rflags

  _register_ctx_fmt_t() : rax(0),
    rip(0),
    rsp(0),
    eflag(0) {
  }
} regs{};

Finally, knowing that IDTR & GDTR uses the same struct as the segment registers:

			rsp(0),

		}

Both lines, last and sencond to last, are added because in the manual mentions that this implementation may store in the memory area pointed to a Host Save Area, thats why we create a pointer to a Physical Address _pa:

VM_HSAVE_AREA

This may be the most technical part, in terms of hypervisors, of all, but not the most complex. We have to go back to the manual to read again 2.2.1 Basic Operation mainly:

Software must load RAX (EAX in 32-bit mode) with the physical address of the VMCB, a 4-Kbyte-aligned page that describes a virtual machine to be executed

As I said before, this is not a focus hypervisor blog, so you just have to trust me and know a little bit of how paging works in low level programming.

static VOID ObtainGDTR(_Inout_ seg_register& vcpu) {

		(unsigned long long)gdtr[8] << 48 |
		(unsigned long long)gdtr[7] << 40 |
		(unsigned long long)gdtr[6] << 32 |
		(unsigned long long)gdtr[5] << 24 |
		(unsigned long long)gdtr[4] << 16 |
		(unsigned long long)gdtr[3] << 8 |
		(unsigned long long)gdtr[2];
	unsigned short gdtrLimit = (unsigned int)gdtr[1] << 8 |
		(unsigned int)gdtr[0];

	DbgPrint("[SVM] Global Descriptor Table Register base: 0x%llx, limit: 0x%X\r\n", gdtrBase, gdtrLimit);

		procIndex, HostState->gdtr.base_addr, HostState->gdtr.limit, HostState->idtr.base_addr, HostState->idtr.limit);

  return TRUE;
}

static VOID ObtainIDTR(_Inout_ seg_register& vcpu) {
	unsigned char idtr[10] = { 0 };
	__sidt(idtr);
	unsigned long long idtrBase = (unsigned long long)idtr[9] << 56 |
		(unsigned long long)idtr[8] << 48 |
		(unsigned long long)idtr[7] << 40 |
		(unsigned long long)idtr[6] << 32 |
		(unsigned long long)idtr[5] << 24 |
		(unsigned long long)idtr[4] << 16 |
		(unsigned long long)idtr[3] << 8 |
		(unsigned long long)idtr[2];
	unsigned short idtrLimit = (unsigned int)idtr[1] << 8 |
		(unsigned int)idtr[0];

	DbgPrint("[SVM] Interrupt Descriptor Table Register base: 0x%llx, limit: 0x%X\r\n", idtrBase, idtrLimit);
	vcpu.base_addr = idtrBase;
	vcpu.limit = idtrLimit;
}

Segment Registers

Once again, we run into the same problem we had with the pseudo-descriptors. Windows do not support functions to read memory from a location speficied by an offset relative of a segment register, only for GS and FS.

https://learn.microsoft.com/en-us/cpp/intrinsics/readgsbyte-readgsdword-readgsqword-readgsword?view=msvc-170 https://learn.microsoft.com/en-us/cpp/intrinsics/readfsbyte-readfsdword-readfsqword-readfsword?view=msvc-170

But we are more than microsoft, or that we want to be. Therefore the implementation of FillSegmentInfo() and some asm functions. Let’s start with the content of the function mentioned:

static VOID FillSegmentInfo(seg_register& seg, UINT16 selector)
{
	seg.selector = selector;
	seg.limit = (selector != 0) ? static_cast<UINT32>(__segmentlimit(selector)) : 0;
	seg.attribute.value = (selector != 0) ? AsmReadSegAttributes(selector) : 0;
	seg.base_addr = 0;
}

May sound complicated, but is just a storing function that takes from arguments the structure to be stored, in our case HostState->cs; and the segment register content that will be passthrought from the assembly function AsmReadCS().

Also, the function AsmReadSegAttributes is an assembly code to get the attributes from a register, for more information read:

https://revers.engineering/day-4-vmcs-segmentation-ops/

AsmReadSegAttributes proc
; RCX = selector (16/32 bits)
lar rax, rcx
jz  @f
xor rax, rax
ret
@@:
shr rax, 8
and rax, 0F0FFh      ; attrib bits for VMCS/VMCB
ret
AsmReadSegAttributes endp

Also, every AsmReadCS/ES/DS/SS() has the same structure, in an example we will do the Code Segment:

AsmReadCS proc
mov ax, cs
ret
AsmReadCS endp

Doing that, we insert the .asm files in our visual project and in the header file extern them:

extern HOST_STATE* g_HostState;
BOOLEAN HostInfoGather(_Inout_ HOST_STATE*);

// Definitions
BOOLEAN HostInfoGather(_Inout_ HOST_STATE* HostState) {
  if (!HostState)
  	return FALSE;

  const ULONG procIndex = KeGetCurrentProcessorNumberEx(nullptr);

  if (!HostState->p_hsave_pa)
  {
    PHYSICAL_ADDRESS lowAddr;  lowAddr.QuadPart = 0;
    PHYSICAL_ADDRESS highAddr; highAddr.QuadPart = MAXULONG64;
    PHYSICAL_ADDRESS boundary; boundary.QuadPart = 0x100000000ULL; // 4GB
    
    HostState->p_hsave_pa = MmAllocateContiguousMemorySpecifyCache(
      PAGE_SIZE, lowAddr, highAddr, boundary, MmCached);

    if (!HostState->p_hsave_pa) {
      DbgPrint("[SVM][CPU %u] Error: while asigning 4KB for HostSave\n", procIndex);
      return FALSE;
    }

    RtlZeroMemory(HostState->p_hsave_pa, PAGE_SIZE);
    HostState->hsave_pa = static_cast<UINT64>(MmGetPhysicalAddress(HostState->p_hsave_pa).QuadPart);
    DbgPrint("[SVM][CPU %u] HostSave asigned @ VA: 0x%p | PA: 0x%016llX\n",
      procIndex, HostState->p_hsave_pa, HostState->hsave_pa);
  }
  __writemsr(amd64_hsave_pa, HostState->hsave_pa);  
  DbgPrint("[SVM][CPU %u] MSR VM_HSAVE_PA (0x%08X): 0x%016llX\n",
    procIndex, amd64_hsave_pa, HostState->hsave_pa);

  // CR0, CR3, CR4, EFER - Host paging/operating mode
  HostState->cr0 = __readcr0();
  HostState->cr3 = __readcr3();
  HostState->cr4 = __readcr4();
  HostState->efer = __readmsr(amd64_efer);
  DbgPrint("[SVM][CPU %u] CR0=0x%016llX CR3=0x%016llX CR4=0x%016llX EFER=0x%016llX\n",
    procIndex, HostState->cr0, HostState->cr3, HostState->cr4, HostState->efer);

  // RFLAGS
  HostState->regs.eflag = __readeflags();
  DbgPrint("[SVM][CPU %u] RFLAGS=0x%016llX\n",
    procIndex, HostState->regs.eflag);

  // IDTR, GDTR - The pseudo-descriptors. 
  ObtainIDTR(HostState->idtr);
  ObtainGDTR(HostState->gdtr);
  DbgPrint("[SVM][CPU %u] GDTR base=0x%016llX limit=0x%04X | IDTR base=0x%016llX limit=0x%04X\n",
    procIndex, HostState->gdtr.base_addr, HostState->gdtr.limit, HostState->idtr.base_addr, HostState->idtr.limit);


  // CS.SEL, DS.SEL, ES.SEL, SS.SEL
  FillSegmentInfo(HostState->cs, AsmReadCS());
  FillSegmentInfo(HostState->ss, AsmReadSS());
  DbgPrint("[SVM][CPU %u] CS=0x%04X (lim=0x%08X attr=0x%04X) | DS=0x%04X (lim=0x%08X attr=0x%04X)\n",
    procIndex, HostState->cs.selector, HostState->cs.limit, HostState->cs.attribute.value,HostState->ds.selector, HostState->ds.limit, HostState->ds.attribute.value);

  FillSegmentInfo(HostState->ds, AsmReadDS());
  FillSegmentInfo(HostState->es, AsmReadES());
  DbgPrint("[SVM][CPU %u] ES=0x%04X (lim=0x%08X attr=0x%04X) | SS=0x%04X (lim=0x%08X attr=0x%04X)\n",
    procIndex, HostState->es.selector, HostState->es.limit, HostState->es.attribute.value,HostState->ss.selector, HostState->ss.limit, HostState->ss.attribute.value);
  return TRUE;
}
